# M8.2 — current cREXX built natively on VM/370plus (done 15 October 2026, route 2)

**Goal:** build current cREXX (adesutherland/crexx 77ba820c3) on CMS with
GCC380 and GCCLIB31. The modules are RXC82, RXAS82 and RXBVM82. They sit
beside M8.1's cross-built RXC8, RXAS8 and RXBVM8; VM/370plus ships both.

## The charset decision
GCC380 runs on an EBCDIC system and compiles string and character literals
as EBCDIC. It has no option for an ASCII execution character set. So the
native cREXX runs in EBCDIC, as IBM REXX on CMS does:
- **Scanners:** regenerated with `re2c -e`, using upstream's own
  `S370/encoding.re`. The largest one shrinks from 232,000 lines to 11,000.
- **UTF-8:** `utf.h` is replaced by a single-byte version (`m82/inc/utf.h`,
  one byte is one character, case from the C library), and `NUTF8` is
  defined.
- **Library:** it must be compiled natively too. The PC-built `LIBRARY
  RXBIN` holds UTF-8 strings and IEEE doubles; GCC380 uses hexadecimal
  floating point.

## Pipeline (`arch/31bit/m82/`)
1. `prep.py`
   - stages the 113 sources and every header they reach under 8-character
     CMS names;
   - rewrites the `#include` lines;
   - applies the native-CMS deltas (platform.c: file probe and dirent under
     `CREXX_CMS_GCC`).
2. `pre.sh`: compiles the staged tree on the PC (s390x gcc `-m31`) against
   GCCLIB31's headers, to find missing declarations and symbols.
3. `names.py`: gives the 1,109 externals that are longer than 8 characters
   (or collide when cut to 8) a short name, `CXnnnnn`. `prep.py` then
   renames them textually; macros were not enough, because cREXX `#undef`s
   some of the names.
4. `xf/xform.py`, per unit:
   - preprocesses the unit, parses it with pycparser, prunes it to the
     declarations it reaches, and works out expression types;
   - rewrites the code to get round GCC380 (next section);
   - writes one self-contained C file.
5. `mkcms.py` writes the reader deck: every unit, the table CSECTs,
   `CRX82MK EXEC`, the PARM files and `PDPTOP COPY`.
6. `mkrun.py` writes the drive.py run. In `full` mode it formats CMSUSER's
   194 as A, loads the deck and runs CRX82MK.

## Runtime layer over GCCLIB31
- **`CRXRT C`** supplies:
  - the printf family with C99 length modifiers (`%lld`, `%zu`, ...) and
    real `snprintf`;
  - `strtoll`, `strtoull`, `strdup` and the other missing string and number
    routines;
  - CMS file names: cREXX's `dir/fn.ft` becomes `FN FT M`;
  - `stat`, and `opendir`/`readdir` built on `LISTFILE * * m (EXEC`.
- **`CRXLGCC C`** supplies:
  - the 64-bit helpers GCC380 calls but nothing provides: `@@DIVDI3`,
    `@@UDIVDI`, `@@MODDI3`, `@@UMODDI`, `@@MULDI3`, `@@NEGDI2`, `@@CMPDI2`,
    `@@FIXDFDI`, `@@FIXUNS`, `@@FLOATD`;
  - `crxadd64`, `crxsub64`, `crxadt64`, `crxinc64`, `crxcmp64`, `crxucm64`
    and `crxsw64`.

  Everything in it is written with 32-bit arithmetic only.

## GCC380 defects found (each measured on CMS with small test units)
| Defect | Fix |
|---|---|
| No 64-bit add: every `long long +`, and every `- constant`, crashes the compiler with an internal error | xform turns 64-bit `+ - += -= ++ --` into helper calls |
| 64-bit compares under `&&`/`\|\|` are folded into range tests, which need an add | all 64-bit compares and truth tests become calls |
| "Unable to generate reloads" for the DImode compare-and-branch in large functions | same as the row above |
| `SLDA` used for 64-bit `<<` (keeps the sign bit) | `SLDA OPSYN SLDL` as the first statement of PDPTOP COPY (CRX82 MACLIB) |
| 64-bit libcalls made through `=A(@@...)` without EXTRN, which does not assemble | EXTRN for them in PDPTOP COPY |
| unsigned 64-bit to double: small odd values come out wrong | open; not used by cREXX as far as we know |

## Assembler and CMS limits found
| Limit | Fix |
|---|---|
| A CMS file holds 65,533 records | a unit is split into parts: statics become externals `CYnnnnn`, and each part defines some of the functions and declares the rest |
| About 400 ESD entries per assembly (IFO264, "too many ESD entries") | parts are cut on a budget of 330 external symbols |
| The VM's run() calls about 680 outlined handlers by itself | it calls them through a table that each part fills in once |
| Lemon parser tables of 68,000 entries (one DC line per element) | the tables become assembler CSECTs `CTnnnnn`, with `DC X'..'` lines of 26 bytes each |
| `CREXX_VM_HANDLER_PANEL` 20 inlines the handlers into run() | the native build sets 1, so the handlers are out of line |
| GCCLIB31 stdio handles at most 32,768 records per file | the ASMFIX filter idea was dropped; PDPTOP does its job |

## More GCC380 defects (9-10 October)
| Defect | Fix |
|---|---|
| A 32-bit constant expression widened to 64 bits (`(uint64_t)sizeof x`, enum values) lands in the high half | xform widens them at run time (`crxs64`/`crxz64`) |
| Small 64-bit literals with suffixes (`7ULL`, `UINT64_C(0x7F)`) and folded ones (`~0ULL`): the same MVC 8 from a 4-byte literal | xform folds literal expressions in 64-bit arithmetic and uses `crxkN` statics; also for `& \| ^` with 64-bit operands |
| `x & (unsigned char)(1 << n)` tested for non-zero: a wrong bit test (the RXBIN LZSS decoder) | the shift goes through `crxid32()` |
| Inlined functions with 64-bit parameters get an argument as 0 (the VM's `rxinteger_checked_add`) | no inlining in the native build (`inline` defined away) |

## Character set and floating point (10 October)
| Problem | Fix |
|---|---|
| re2c's EBCDIC mode is code page 037; VM/370plus is IBM-1047 throughout (Hercules `CODEPAGE 819/1047`, GCC380, every text file): `[ ] ^` did not scan | `re2c/ebcdic.h`, re2c's table for 1047 with `\n` = X'15' (NL); `mkscan.sh` builds that re2c and generates the four scanners |
| The section sign of internal names (`§this`, `§factory`, `§match`) is written both as the escape `"\xc2\xa7"` and as literal UTF-8, and counted as 2 bytes. The reader translates the literal; GCC380 translates escaped high bytes and joins `"\xc2\xa7" "factory"` before reading the escape | staging writes both as `"_#"` (2 bytes); rxvml's byte test matches |
| Hexadecimal floating point: the number formatter divided by `pow(10, exp)`; a zero divisor raises a program check (IEEE would give infinity) | scaled in two steps on CMS, with a `CRX:` diagnostic line |
| CRXRT's printf engine dropped a `*` precision (`%.*lf`) | the float conversion is rebuilt from the parsed fields |
| GCC380 loads a 64-bit value through a pointer as `L R,a(R); L R+1,4+a(R)` | DIMFIX (between GCC380 and ASMAHL) makes it `LM`, with `LA` first when the address has an index register |

`-O0` was tried for the class problem: it changes nothing there and one
unit (RXASFLO9) no longer assembles, so the build stays at `-O1`.

## Disks
The source deck is about 35,000 blocks; with the objects and modules the
build fills 194 to about 76%. READCARD ignores a `:READ` filemode, so the
deck stays on A. The library is built on CMSUSER's 197.

## Test aids
- `prep.py` with `M82TRACE=file.c` marks every `return 0`/`goto error` of a staged
  file; RXBVM82 prints the last 16 on a load error.
- `xf/pcfix.py` makes an xform output unit build for s390x Linux (real varargs,
  C library stdio for GCCLIB's CRAB). The transformed RXBVM82 then runs under
  `qemu-s390x` on the PC: when that copy is right and the CMS one is not, the
  fault is GCC380's code generation, not xform.
- Decoding a CMS-written RXBIN on the PC and comparing it with the PC's own
  found the varint writer bug.

## Route 2: GCC 13 on CMS (15 October)

The owner's decision of 12 October (9.21) moved native C on CMS from GCC380 to
GCC 13: `cc1`, `as`, `ld` and `ar` now run on CMS. With them, M8.2 no longer
needs any of route 1's workarounds. There is no xform, no 8-character renaming,
no table CSECTs, and no hexadecimal floating point. CMS compiles exactly
the sources M8.1 cross-compiles, with the same flags.

- `m8/units.sh`: the unit lists and flags, shared by `m8/build.sh` (M8.1)
  and `m8/native/mknat.sh`.
- `m8/native/mknat.sh SYSROOT.tar OUT` writes:
  - `crxroot.tar`: LANG's SYSROOT TAR plus every cREXX source and header the
    113 units reach (from the PC compiler's `-MD` lists), under `/crexx/s`
    (source tree), `/crexx/h` (the host build's generated C), `/crexx/g` and
    `/crexx/cms`.
    - cmsrt's sysroot VFS matches names literally. Includes such as
      `"../platform/x.h"` are therefore also stored under the path cc1 asks
      for (`crexx/s/rxpa/../platform/x.h`, 33 of them).
  - `crx82.exec`, `CRX82 EXEC`:
    - First it renames CRXROOT TAR to SYSROOT TAR (keeping the original as
      SYSROOT0); `CRX82 DONE` gives the names back.
    - Then cc1 + as per unit. A unit whose `O` file exists is skipped, so the
      build can be restarted.
    - Then `ar` (the VM and assembler units, for RXC), `ld`, `XL ELF2CM8`
      (elf_to_cms with the 8 MB image limit; RXC is 4.4 MB) and
      LOAD/GENMOD → `RXBVM82`, `RXAS82` and `RXC82 MODULE`.
  - `pc/`: the same recipe on the PC, which gives the reference TEXT decks.
    It links cleanly; the sizes match M8.1.
- Run: `tests/runs/m82-native-gcc13.json`, started with
  `tools/esa390mb.sh 256` (see below). The steps:
  - CMSUSER at 256M, IPL 290;
  - the profile, then Enter (it waits for one);
  - `LINK MAINT 19F 29F MR` (password MULT), `ACCESS 29F A`;
  - `CRX82`, then the test programs C82HELLO and C82LIB.

### What the runs found
| Finding | What it was |
|---|---|
| `DEVICE ERROR` accessing LANG, FORMAT of an EDF TDISK refused | `ACCESS (NOPROF` skips SYSPROFX, which loads DMSEFS: setup, not a defect |
| REXX EXECs give `Ready(-0003)` | the same NOPROF; the CMS profile must run (and wants one Enter) |
| After a write to one EDF disk, files on a second EDF disk are not found; `DMSFRE161T` at a later RELEASE | **I-297**, open. Worked around: everything on one EDF disk (LANG R/W as A) |
| CP in an enabled wait after 7 minutes of cc1 | **I-272**: the run had MAINSIZE 16 (`esa390.sh` sets it on purpose); real storage exhausted. Big runs use `esa390mb.sh 256` |
| `fatal error: ../platform/rxinteger.h` | the literal-name VFS (above) |
| a container restart at 07:50 killed Hercules | images checked with `cckdcdsk -3`: free space rebuilt only; the build resumed from its O files |

Speed, MAINSIZE 256: the small units take about 70 s each, including
loading the 23 MB CC1 XIMAGE and the 21 MB tar every time.

What it took, beyond the first findings above:
| Problem | Fix |
|---|---|
| cc1 out of heap on rxvmintp.c (several runs) | (1) cmsrt's `read_whole` doubled its buffer: a 21 MB tar took 32 MB and left 16 MB of holes. It now sizes the buffer once from the FST. (2) cmsrt's heap came from a coarse list (232, 224, 192, 160 MB), so cc1 got 160 of 187 MB; it now takes the largest HIGHSTOR piece in 4 MB steps. (3) XL read the whole XIMAGE before allocating the image, leaving a 23 MB hole; `cms_read_head` reads the header first. (4) `--param ggc-min-expand=20 ggc-min-heapsize=32768`. (5) `CREXX_VM_HANDLER_PANEL=1` (the handlers out of line) |
| rexbscan.c (re2c `-8`, Unicode letters: 3.2 MB, one function) needs about 260 MB of GC data: more than a 256M machine (CP's ceiling, I-185) | upstream's own CMS recipe (S370/cmslocalbuild.sh): re2c with `S370/encoding.re` (letters a-z A-Z). rexbscan 169 KB, rexcscan 19 KB, rxcposcn 32 KB. Identifiers are ASCII letters only, as in IBM REXX |
| `ar: could not create temporary file whilst writing archive` | open; RXC is linked from the members the PC's link of the same objects takes from the archive (47 of 51) |
| `AR rcs ...` upper-cased by CMS; `CALL LINK 'X',` at a line end is a continuation, not a separator | all ar arguments in the stack; `'X', ,` |
| cc1 probes `x.h.gch`; CMS said `Invalid mode 'GC'` each time | cmsrt: a third name part must be a mode (letter + digit) |
